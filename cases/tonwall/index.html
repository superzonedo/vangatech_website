Before

The problem was never a missing spreadsheet

The company already had its Excel reports, and they worked. The bottleneck sat upstream: getting data out of emails and attachments and into those reports was almost entirely manual. Someone opened each supplier invoice, keyed in line items one by one, searched back through history to see whether a part number had been logged before, looked up the current exchange rate, and then decided which tariff rate to trust.

Each of those steps is slow, and each of them fails quietly when the day gets busy:

Line-by-line data entry

Invoices were keyed in by hand — which means items get skipped, mistyped, or entered twice with nobody noticing until reconciliation.

New part numbers stall the flow

When a part number appeared for the first time, the process jammed on a question nobody owned: should this be recorded yet, or not?

Tariff rates lived in memory

Rates came from digging through past declarations and personal experience. Where a number came from — and how much to trust it — was not visible on the page.

Exchange rates drift

FX had to be looked up and updated separately. Easy to forget, and every time it's forgotten the cost analysis quietly stops being consistent.

Where the line is drawn

This system does not replace customs judgment. It automates the data handling that can be standardized, so that human attention lands on the exceptions that actually need a decision.

Solution

Five stages, one human gate

Work that used to be scattered across an inbox, a browser and a spreadsheet becomes one traceable chain. Each stage is independent and re-runnable, so a failure in one doesn't contaminate the others — and what staff finally see is data that has already been organized, with its status and source attached.

Intake from a designated mailbox

Supplier invoices arriving as PDF or image attachments are picked up from one specified mailbox. Nothing else in the inbox is touched.

Read the invoice, split out the fields

Invoice number, description, quantity, unit price, weight and country of origin are extracted from PDFs, scans and photographed invoices, then reshaped into the invoice header, line-item and cost-analysis fields the company's report expects.

Match against history, check for duplicates

Line items are compared against previously registered part numbers to reduce mismatches. The same email or the same invoice arriving twice is caught before it can be booked twice.

Write into the existing report

Output goes into the designated sheets and columns of the company's own Excel workbook — no new system for anyone to learn, and every value carries its source and status.

Human confirmationHUMAN GATE

New part numbers, low-confidence fields and AI-suggested tariff rates sit in a pending state for review. Before anything is filed as a customs declaration, a person — company staff or the customs broker — confirms it. The system never promotes an unconfirmed suggestion to a final answer.

Tariff Logic

Cheap and certain first. AI last, and clearly labelled.

When a new part number needs a tariff rate, the system works down an order of preference — from most reliable and cheapest to least certain. AI is only consulted when neither history nor similar records can answer, and its answer is never presented as settled.

▲ Every confirmation makes the next identical case cheaper — the answer moves up to Tier 01 permanently

That last arrow is the part that compounds. A rate confirmed once stops being a lookup forever: the next invoice with the same HS code resolves at Tier 01, without an API call and without a review queue entry. The system gets cheaper to run the longer it runs, and the company's accumulated knowledge stays inside the company.

Hard limit

AI only ever suggests. Before a declaration is formally filed, company staff or the customs broker must confirm the rate. An unconfirmed suggestion is never packaged as a final answer — not in the report, not in the export, not anywhere.

FX

Exchange rates update themselves — from somewhere else

A separate, independent tool fetches and updates FX rates on a schedule, so cost analysis always runs on one consistent and reasonably current number instead of whatever was last pasted in. Keeping it separate from invoice processing is a permissions decision, not a packaging one: the tool that reaches out to the public internet is not the tool holding the invoice pipeline's access.

Design point

The FX tool only does FX. The invoice tool only does invoices. Split this way, permissions, maintenance and blast radius all stay small enough to reason about.

Security Architecture

Least privilege, drawn as a boundary

The point of the security design isn't to give every component the same broad set of permissions — it's to separate the core data flow from the parts that need to query outward. The invoice core reads one designated mailbox and writes one designated report through controlled Google authorization. It does not call public FX or AI services itself.

▲ Two tools cross the boundary outward. The invoice core is not one of them.
SCOPE 01

Invoice core

Reads the designated mailbox and nothing else; writes the designated company report and nothing else.

SCOPE 02

FX tool

Holds only the permissions the FX service requires. No mailbox access, no report-wide access.

SCOPE 03

Tariff tool

Calls AI only when the first two tiers come back empty, and returns the suggestion together with its source status.

SCOPE 04

API keys

Stored in Google's backend security settings. They never appear in the report, in a file, or in the code.

SCOPE 05

Fault isolation

If an outward-querying tool breaks, the failure stays there. It does not escalate into a risk to the invoice data flow.

SCOPE 06

Honest phrasing

We don't claim the core is "completely offline". The accurate statement is narrower — and we prefer the accurate one.

How we describe it

Rather than saying the core system is "completely disconnected from the internet", the precise statement is this: the core does not call public network services directly. It accesses the designated mailbox and report through controlled Google authorization.

Review & Governance

Automation reduces repetition, not accountability

The system's job is to make it obvious which data is backed by confirmed history, which is new, and which is only a suggestion. Four paths through review:

CaseWhat happens
RoutineBacked by confirmed history. Quick check, then booked.
New part numberPart number, description and application are confirmed first, then stored as a record future invoices can reuse.
AI-suggested rateTreated as formal data only after company staff or the customs broker confirm it.
ExceptionKeeps its error or pending state deliberately — the goal is no silent failure.

Acceptance criteria we're holding ourselves to

  • Extraction completeness — every required field either has a value or an explicit marker saying it's missing.
  • Write accuracy — columns, sheets and data types conform to the existing report's rules.
  • Exception visibility — new part numbers, low-confidence data and AI suggestions can all be reviewed in one place.
  • Duplicate protection — the same email or invoice cannot be booked twice.
  • Permission conformance — each tool holds only the permissions its own job requires.

Automate what can be automated. Mark clearly what isn't certain. Keep sensitive data and outward permissions permanently apart.
