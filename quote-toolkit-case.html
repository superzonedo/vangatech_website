Before

The manual process couldn't keep up with a thousand part numbers

Maintaining an electronic-components pricebook used to look like this: an engineer opens a distributor's website, searches one part number at a time, and copies each quantity-tier price into Excel by hand. Thousands of parts. Multiple distributors. Prices that never stop moving.

Before the rollout, we found every classic hand-copy failure already living in the file: prices pasted under the wrong quantity column (a 5-piece price sitting in the "10 pc" column), prices updated without touching the date column (fresh data that looks stale), copy-paste rows where someone forgot to change the numbers. Every one of those errors eventually becomes a wrong quote in a customer's inbox.

Solution

Five steps, one human gate

The workflow is split into independent, repeatable steps. If any step fails, it can be rerun on its own without contaminating anything else.

Scan the pricebook for lookup targets

Automatically lists parts whose price cells are empty or past their freshness threshold. Specific rows can also be queued by hand.

Batch lookups via official distributor APIs

Uses the official APIs of DigiKey, TME, and other distributors — not scraping. Responses are structured quantity tiers and unit prices; no "have an AI read the screen and guess the numbers."

Automatic triage: clean data vs. needs-a-human

Exact part-number match with clean data → the write queue. Part not found, multiple candidates, or a part number that looks like a spec description → the human-review queue, each with a problem description and a suggested action.

Human reviewHUMAN GATE

The only step that needs a person — and it's kept that way on purpose. Picking the wrong part number changes real quote amounts. That judgment stays with a human; the system never guesses.

Write back to Excel + generate a changelog

Output goes to a new file (the original is never overwritten). Every price cell carries a full annotation, and a Markdown changelog is generated as an audit trail.

Trust by Design

Why it can be trusted with a pricebook

The biggest risk in automation isn't "couldn't find it" — it's writing the wrong thing, quietly. Every design rule in this toolkit answers a failure we actually encountered:

RULE 01

Never guess a part number

When a part isn't found — even if the system sees a "close enough" candidate — it goes to human review. It is never substituted automatically.

RULE 02

Never overwrite the original file

All output is written to a new file. The source pricebook is untouched end to end; a person decides if and when to replace it.

RULE 03

Never bulk-clear old data

Only cells with fresh data are overwritten. Removing an old tier requires an explicit human instruction. Valid old data that wasn't part of this run is never touched.

RULE 04

Every cell is traceable

Each written price carries a cell comment: distributor, product URL, query date, and the change versus the previous price. Audits never require opening another system.

RULE 05

Credentials stay out of the code

API credentials live in a separate environment file — never in version control, never in config files or source code.

RULE 06

State is visible

Parts that couldn't be queried (e.g. API quota exhausted) are marked grey — "not yet queried" — in the sheet. No blank cell ever pretends it was checked.

Routing

Which part goes to which distributor — rules decide, not habit

Different brands belong at different distributors: house-brand parts are listed with distributor A, third-party brands are best stocked at distributor B. Those rules live in a config file, not hard-coded in the program:

BRAND valueRouting behaviorAction
contains "TME"House part, known to be listed with TMEQuery TME
third-party brandPurchased component, best coverage at DigiKeyQuery DigiKey
house brand onlyMade in-house; distributors won't have itSkip automatically

The same principle runs through the whole toolkit: a new pricebook format = one new config file (which row holds the headers, which column holds part numbers, where the price block sits), and a new distributor = one new fetch script. The core program doesn't change by a single line.

Data Security

Security decided at the architecture level

The pricebook never leaves the client's machine

The entire toolkit runs locally. Excel files, cost structures, customer information — none of it passes through any third-party server.

Only part numbers go out

The only data ever transmitted is the part-number string — the same thing anyone can type into a distributor's public search box. Prices and quantities flow in, never out.

Official APIs, not scraping

Lookups go through the channels distributors provide for exactly this purpose: business batch pricing. No terms-of-service violations, and no breakage every time a website redesigns.

Credentials handled separately

API keys live in an environment file excluded from version control, and key-management practices are handed over as part of delivery.
