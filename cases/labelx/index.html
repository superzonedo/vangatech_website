Before

A label is public information nobody can actually read

A shopper holding a box of cereal runs into three walls at once: vocabulary (a chemical name means nothing without a toxicology background), context (22g of sugar is unremarkable in jam and alarming in a yogurt drink — the number alone is noise), and relevance (someone with kidney disease and someone training for a marathon shouldn't get the same warning from the same label).

Most scanner apps fail a fourth way on top of that: they hand back a single number with no justification. A score you can't interrogate is a score you can't trust — and the moment it contradicts a user's intuition once, they stop trusting it entirely.

Product goal

Not "score the food." Produce a defensible, auditable, personally relevant verdict — fast enough to use standing in a supermarket aisle.

Solution

A photo in, a typed verdict out

The user photographs a label or picks one from the library. The client compresses the image and sends it to the backend; the AI layer returns a fully typed analysis object in a few seconds on an ordinary mobile connection. Every score comes with its own audit trail: an itemized breakdown of every deduction, the literal arithmetic behind the final number, the one to three factors that actually moved it, and what would have to change for the product to score better.

System Architecture

Four zones, one typed contract running through all of them

The camera captures and compresses the image on-device, a serverless API layer authenticates the request and checks entitlement, the AI layer routes to the right model tier and enforces a strict response schema, and the result is persisted alongside the original image.

Engineering Highlights

The hard part of an AI product isn't calling the API

01

A deterministic scoring engine

The score is not the model's opinion — it's a rule system the AI is instructed to apply, so the same label produces a comparable score every time and every deduction traces to a rule. Position weighting stops a trace ingredient from tanking a score; context rules stop fermented and traditional foods from being penalized like instant noodles; anti-gaming guards stop a sugar-loaded drink from buying back points with a vitamin fortification claim.

02

Schema-constrained AI output

Every request carries a strict response schema covering product identity, additives, nutrition, NOVA class, traffic lights, and the score breakdown. The client parses a guaranteed shape — no regex scraping, no defensive string surgery. The schema also forces the model to declare its own uncertainty, so a blurry photo produces a flagged low-confidence answer instead of a confident wrong one.

03

Two-tier model routing

Requests carry a mode — a fast, cheaper tier for routine scoring, a stronger tier for detailed explanation. Model selection happens server-side against a hard allowlist, so a client can't request an arbitrary model string. It's a cost control and a security control at once.

04

Localization reaching into the AI layer

Three languages, including full Traditional-vs-Simplified Chinese enforcement. The response schema instructs the model to produce names, warnings, and recommendations directly in the target language — nothing is machine-translated after the fact, so nutritional terminology stays correct in each locale.

05

A security model where the client can't lie

Database rules refuse client-side writes to privileged fields outright. Scan records are writable only by backend functions running with admin privileges, and subscription/entitlement fields live where the client has no write path at all — so a modified client can't forge its own subscription state.

06

An image pipeline that fails soft

Photos are resized and re-encoded before upload for a large size reduction with no meaningful loss in label legibility. If compression errors out, the original image uploads rather than failing the scan — and a hard size ceiling catches an oversized payload with a helpful message instead of a server timeout.

A photo, an itemized score, and one hard rule: personalization never touches the number.

Personalization without score contamination

It's tempting to fold a user's health profile into the score — a diabetic sees a lower number on a sugary product, done. LabelX does the opposite, and the AI prompt enforces it explicitly: personalization must never modify the health score.

A score that shifts per person isn't a score, it's an opinion — it can't be compared across users, can't be cached or shared, and turns a history trend line meaningless the moment the user edits their profile. So the two stay structurally separate: the score is objective and shareable, and the personalized layer is a distinct advisory surface — condition-specific warnings, an individual risk assessment, a tailored recommendation. A product can score 85 and still carry a red personal warning for sesame. Both are true, and neither corrupts the other.

How It Was Built

Prove the hard part first, monetize last

The build ran in overlapping phases, but the sequence of technical milestones was deliberate.

Design system extraction

The visual language was pulled into a standalone component workspace — color system, typography, radius scale, light/dark theming — and settled in a browser before it had to survive a mobile build cycle.

The analysis backend

The riskiest part went first: serverless endpoints, the response schema, the scoring rules, and the data model, validated independently of any UI. If the analysis quality wasn't achievable, nothing else mattered.

The application

Navigation shell, camera and library capture, result presentation, history with search and filtering, and the home dashboard — with local state persistence so the app stays useful on intermittent connectivity.

Identity and personalization

Sign in with Apple and Google Sign-In, the onboarding questionnaire, profile persistence, and the personalized analysis layer. A reinstalling user recovers subscription state and preferences from the server rather than losing them.

Localization and responsive layout

Three-language rollout including native permission strings, plus a full responsive pass across device sizes and orientations.

Monetization

Paywall placement, entitlement synchronization after login, and server-side entitlement verification — never client-side trust.

Release engineeringSHIPPED

Signing and provisioning, release-mode builds, store metadata and assets, and the submission pipeline through to a live App Store release — plus the runbooks to reproduce all of it.

What This Demonstrates

The surface a modern consumer AI product actually needs

  • AI product engineering beyond calling an API — schema-constrained output, a deterministic rule layer on top of a probabilistic model, explainability as a first-class feature, cost-tiered routing, and an instrumented harness for measuring prompt changes rather than guessing at them.
  • Serverless backend architecture — scale-to-zero economics, secret management, and a security-rule model where a compromised client can't escalate privileges.
  • Identity and compliance — Apple and Google sign-in, session persistence, cross-device state recovery, and account deletion — the requirements that block App Store review when they're an afterthought.
  • Monetization done right — paywall integration with server-side entitlement verification, not client-side trust.
  • Internationalization done properly — locale awareness reaching into the AI output layer, not just a translation pass at the end.
  • Release engineering — signing, provisioning, store assets, and a submission pipeline that reached a live release, with documentation to reproduce it.
  • Design-to-code discipline — a design system extracted into a real, buildable token layer before implementation, so the shipped product matches the design instead of approximating it.
